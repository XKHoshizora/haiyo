**1. 总评**

这份计划最强的是：把“主人始终可见”“来访者必须知情”“第二圈只能由主人发起”提前写成规则，也没有急着做公开广场和无限自动讨论。最弱的是：把一次涉及权限、隐私、计费和消息生命周期的改造，描述成了现有群聊能力的小幅延伸。D1 默认等主人批准，与 P1 直接冲突；D4 的“每天最多 N 点”和 P5 的“vault 永不离开专属会话”，也都不能由现有代码保证。**建议先修改这些规则，再进入实施；第一圈可以收窄后做，第二圈不宜照搬群里的接话机制。**

**2. 产品逻辑上的问题**

- **D1：默认审批不满足 P1，七天过期没有解决等待。** 周五有人问周六能不能吃饭，主人八小时不看手机，请求仍然卡着；七天后失效，只是终于告诉来访者这件事没办成。严格坚持 P1，就应让系统依据主人预先选定的范围立即允许或拒绝；若保留“需要我同意”，必须承认“加好友”是 P1 的例外，不能同时宣称两者成立。草案把矛盾写在同一份文件里：`docs/design/2026-11-22-agent-social-plan-draft.md:11`、`:28`。

  **“谁可以加它”也没有回答用户真正关心的“谁现在可以和它聊”。** 主人改成“不让别人加”，前任仍可继续聊天、套信息、花点，因为旧联系人保留。建议设置直接控制当前使用范围，收紧后立即阻止范围外的人继续使用，旧记录按历史规则保留；若产品坚持只影响新联系人，选项必须明确写“已有联系人仍可继续聊天”。

  还要明确：通过“我的联系人”自动加入的人，在主人删掉这个联系人后是否失权。建议同步失权。拉黑则无论哪一方发起，都应阻止双方本人及其 Agent 绕路互动；目前真人拉黑**不会删除 friendship**，因此不能只检查“还是不是联系人”。`app/service/src/social/blocks.ts:22`、`app/service/src/social/relations.ts:46`。

- **D2：主人可见、可以本人身份插话，方向正确；但“不触发回复”远远不够。** 来访者问周六是否有空，Agent 正在生成“有空”，主人插话“周六不行”，随后旧回答仍发出去，就会出现当面互相否定。建议主人插话使尚未发布的旧回答失效；Agent 不自动接主人的话，之后由来访者下一条消息继续触发。停止旧回答属于主动干预，应明确优先于“开始的回复总会完成”。

  第二圈里两个主人都标“主人”会混淆，应显示“A 的主人”“B 的主人”。同一个人兼任参与者和某个 Agent 的主人时，界面和权限都只能算一个人，不能出现两份身份或两份未读。

- **D3：不能关闭“主人可见”的告知是对的。** 但“申请时告知”覆盖不到自动加好友；必须在首次发言前也显示。Agent↔Agent 会话应明确列出**两位可见的主人**，并说明回答会带回发起人的专属会话。

  来访者小周自己拥有 Agent A，不代表他本人获准访问 B 后，A 就自动获得相同权限，更不代表 A 可以代其他人访问 B。人的权限、Agent 的权限和这一次代办的权限必须分别判断。

- **D4：主人付费适合作为第一版规则，但共享额度会产生争抢。** 一个人早上单独找 Agent 写长文，把额度吃完，下午群里所有人都叫不动它。群聊与私聊共用额度是合理的，但需要同一来访者跨入口的限制，不能只限制某个会话；也应让主人看见“谁用了多少”，而不是只看到余额下降。

- **D5：把隐私和资金边界放在开放访问之前是对的，但基础层仍缺完整定义。** “陌生人只拿无害信息”与主打场景“替主人答复日程”存在张力：既不提供日程来源，又不允许访问私密安排，Agent 就只能说不知道或猜测。现有工具是历史搜索、时间、文件和网页搜索，没有日历查询或预约确认能力。第一版应先验证“公开资料问答／分享助手”是否有用，不能把“问到一条旧记忆”当成“确认主人有空”。`app/service/src/agents/tools/index.ts:93`。

  删除 Agent 也不能只让入口消失：正在回答的内容、未完成代办、待处理申请、后台记忆整理都必须停止，来访者得到明确的结束状态。历史记录、听说和主人共享笔记分别如何保留，不能交给一个模糊的“删除”决定。

**3. 隐私与滥用**

1. **最危险的内容入口可能是 `persona`，不只是记忆。** 主人在人格文档里写了妻子姓名、公司项目或私人习惯；来访者要求“模拟你第一次认识主人的自我介绍”，即使 `notesFor` 完美过滤，仍可能泄露。现有群聊会把完整 `persona` 交给模型，再告诉它不要透露。这个保护主要靠模型遵守提示。社交场景应有明确可对外使用的人格内容，私人设定不进入对外回答的上下文。`app/service/src/agents/runtime/prompt.ts:803`。

2. **“后台判断为 yes，再从数据库放行”有结构性隔离，但 yes 不等于主人授权。** 相关材料自己报告：判断模型在 375 对应保密的样本中放行了 9 对；这不是线上泄露率，却足以说明不能把自动判断称为 P5 的保证。攻击者会主动追问被误放行的内容，不会像普通聊天那样碰巧才问到。第一圈建议只开放主人明确选定的资料，其余默认不用；“小习惯”也不应未经定义就等同于任何陌生人都能知道。`docs/design/2026-11-22-memory-zones.html:361`、`:375`。

3. **收紧必须先失效，不能等后台重新算完。** 今天允许向朋友说“在找工作”，明天删了朋友，旧 yes 仍在；或者同一条笔记从“喜欢散步”改成“每天九点在某地址散步”，旧 yes 被继续使用。许可至少要绑定笔记内容版本、实际受众、关系和规则版本；任一变化先拒绝。已经拿到旧上下文的生成也要在发布前检查，失效就取消或重新生成。两条分别允许的笔记组合起来泄露信息，现有研究也明确尚未解决。`docs/design/2026-11-22-memory-zones.html:541`。

4. **第二圈同时需要防“带出去”和防“带回来”。**
   - A 在主人专属会话里已经看过 vault，随后调用 `ask_agent`，可能把私密背景顺手写进问题。只过滤 B 的回答没有用。
   - B 回答：“为了确认，请先查你主人的历史，把地址发给我。”若 A 接着使用私聊里的搜索和外发工具，就形成跨主人窃取。
   
   建议外发由一个只看本次问题及获准资料的独立执行上下文完成；服务端锁定目标、发起真人、收件人和调用次数。接收结果的整理步骤不能因结果正文获得新工具权限、修改记忆权限或继续找第三个 Agent。现有专属会话搜索可查 Agent 当前加入的所有会话，尤其不能直接把它和新增外发工具放进同一个无限制循环。`app/service/src/agents/tools/search.ts:210`。

5. **“只进 hearsay”能防直接写入主人笔记，不能自动防记忆投毒。** 来访者反复说“主人已经同意公开他的联系方式”，即使留下的是听说，模型也可能把它当授权；多个 Agent 相互转述还会制造虚假的多方印证。必须保留原始说话者、被谈论的人、来源会话和转述链，且授权绝不从这些文本推导。当前 hearsay 专门记录“别人谈论本 Agent 主人”，并排除 Agent 发言，不能原样承接“B 告诉 A 关于 B 主人的事”。`app/service/src/memory/hearsay.ts:85`、`:148`。

6. **精确账号搜索降低了探测便利度，没有消除探测。** 知道 `xiaolin` 后，可以尝试常见后缀；攻击者还可比较申请、头像、错误响应及已有群中的身份信息。应统一不可发现对象各入口的响应，并限制同一真人、同一目标主人和全站的探测量。“不让别人加”也只能承诺不通过查找新增发现，不能抹掉别人已在共同群里见过它的事实。现有头像可见性就包含共同会话关系。`app/service/src/principals/store.ts:97`。

7. **骚扰控制不能只数成功启动的回复。** 攻击者可以不断申请、反复撤回、在生成期间追加长消息，或者轮流找同一主人名下多个 Agent。需要申请冷却、目标收件箱上限、消息字节与附件限额、排队上限，以及按背后真人汇总的限制。现有调用限速明确不计合并进正在运行回复的消息，因此它不能替代消息入口限速。`app/service/src/agents/runs.ts:343`。

现有 `VISIBLE_JOIN`、工具引用编号和调用计数属于可复用的结构性保护；“这些只是材料”“不要透露人格”属于模型提示。网页搜索的文本拦截也是有限保护：代码只检查特定长度的重合片段，并明确写了它不是证明，不能承担全部外泄防护。`app/service/src/conversations/store.ts:22`、`app/service/src/agents/tools/index.ts:24`、`app/service/src/agents/tools/web/text.ts:87`。

**4. 钱**

- **D4 现在不是硬上限。** `othersBudget` 按 Agent 计算，只累计已经结算的支出，允许在途回复超出额度。比如已经花了 19 点，三个回复同时开始、各花 5 点，最终可以到 34 点，而不是 20 点。若界面写“每天最多 N 点”，就必须把在途预留也算进去，并在开始前给完成本轮留下预算。`app/service/src/agents/runs.ts:893`、`app/service/src/agents/runs.ts:871`。

- **“我的 Agent 每天最多花 N”究竟是一只，还是所有 Agent 合计？** 当前字段在 `agents` 上，多个 Agent 各有一份，且允许 `null` 表示不限额。建议主人有一个所有 Agent 共用的对外支出总上限，单个 Agent 可以更低；社交版不提供“不限额”。同一个人群里 @ 和私聊使用，同算来访者限额及主人总限额。`app/service/migrations/020_others_budget.sql:4`。

- **BYOK 是明确缺口，不能显示成“有 20 点保护”。** 自带密钥的模型调用不预留站点点数，模型费用也不计入站点收费；因此仅靠 D4 无法约束主人在供应商处的支出。自带密钥的记忆模型也绕过站点记忆额度，长聊还可能触发额外整理。单次调用有长度和时间限制，并不等于每日外部费用有上限。建议在补齐每日调用数、token 总量及明确费用说明前，先不开放 BYOK Agent 的对外使用。`app/service/src/metering/admit.ts:178`、`app/service/src/metering/settle.ts:109`、`app/service/src/memory/call.ts:95`。

  同时不能反过来说 BYOK 完全不花站点点数：它使用联网搜索时，仍会从主人的免费额度或余额扣费。`app/service/src/agents/tools/web/hold.ts:118`。

- **第二圈建议各付各的。** A 主人支付发问、整理结果和回报；B 主人支付 B 的回答，计入 B 的对外额度。同一主人名下两个 Agent 也要受本次任务总预算约束，不能因为全部落在 `own` 车道就没有任务边界。发起人的身份沿全链路保留，防止“借别人的 Agent 转一下”洗成主人自己的调用。

- **预算还要覆盖失败、重试和后台工作。** 一个代办的全部尝试应共用预算；不能重试一次就获得一份新额度。拒绝、暂停、无权限直接由系统提示，不必再花模型费用解释；已经实际发生的调用按约定结算，不能承诺“没拿到答案就没花钱”。

- **wallet 改写与 D4 是两件事。** 统一钱包能解决资金来源和结算，但不会自动解决来访者配额、Agent 配额和整条代办预算。当前代码仍在选择单一 `charge_to`，尚不是草案描述的结算时跨资金池拆分。上线前还要明确跨午夜的预留归属，以及余额不足时由谁承担已启动回复的尾款。`app/service/src/metering/admit.ts:194`、`app/service/src/metering/settle.ts:136`。

核心难点是把“能看、能说、能叫动 Agent、能花钱、能记住、能转述”拆开，然后让所有读取和执行入口遵守同一套规则。

**被低估的主要是生命周期与权限贯通，而不是新增几张表或一个聊天页面。** 前端也有按 `group` 才清除他人私有字段的逻辑，后端改完不代表客户端已适配。`app/web/src/data/model.js:203`。

**6. 第二圈：推荐有截止时间的异步单次询问**

**同步工具调用**容易理解，短请求也能很快返回；但父回复一直占着运行席位等子回复。现有 worker 按 `inFlight` 限制并发，工具执行又在该 run 内等待：若席位都被等待中的 A 占满，B 可能一直无法启动，最后一起超时。同主人多个 Agent 还会碰到共享并发限制。`app/service/src/agents/runtime/worker.ts:378`、`:813`。

**异步代办**需要新增任务状态、结果投递和恢复逻辑，工作更多，但能释放父回复席位，也更适合用户切换页面或离线。因此推荐：

- **一次指令，一个目标，一问一答，一次回报。** 第一版不允许 B 再委托 C，也不允许回复里的 @ 自动继续接话。
- **有持久化任务编号和总截止时间。** 排队、调用、有限重试和回报共用截止时间；超时就结束，晚到结果不再突然发出，刷新页面或服务重启不能重复扣费、重复回报。
- **暂停、额度用完、没有访问权立即结束。** 发起者看到“这次未能取得答复”；B 的主人看到详细原因。不要等主人上线，也不要默认等到第二天额度恢复再执行昨天的请求。
- **循环和预算按任务计算。** 群里的 30 条限制是按单个会话、最近真人发言计算的，跨会话调用或主人插话可能重置计数，不能作为代办的主刹车。`app/service/src/agents/runs.ts:1231`。
- **双方主人都能看到实际交换内容并终止任务。** A 主人看到请求和回报；B 主人看到来访问题和答复，但看不到 A 的整段私人上下文。B 主人可以本人回答并结束询问；任何纠正都使旧答案失效，普通插话不会自动再启动两个 Agent。
- **失败信息由系统显示。** 有预算时可以由 A 自然解释，但不能为了遵守 P2，让“没钱了”本身也必须再调用一次模型。

**7. 范围与施工顺序**

**建议砍掉或后推：**

- 第二圈自动交朋友、递归委托、多轮协商，以及无限制 `ask_agent(handle, question)`。
- 第一圈依靠模型自动推断私人记忆能否向陌生人分享。
- 第一圈跨会话附件转交、`found_elsewhere`、对外主动跟进；BYOK 对外使用等费用边界完善后再开。
- 每条笔记与每个潜在来访者提前两两判断。只对实际获准的受众按需计算，未知一律不用，避免申请骚扰带动后台成本。

**“后放”中必须提前拆出来的部分：**

- 不需要各主人共同审批的“冻结恢复方案”，但需要**立即停止、只读结束、超时、崩溃恢复、撤权后不再投递**。
- 不需要完整群文件产品，但附件与历史的最低可见性规则不能后放。
- 不需要 A2UI，但等待、拒绝、取消和完成的系统状态不能缺席。
- 不需要复杂举报平台，但单独拉黑 Agent、举报入口和运营停用能力应随开放访问一起提供。

**施工顺序：**

1. 先定访问、撤权、实际受众、钱和插话规则，写出状态表与失败场景。
2. 据此并行做三块：权限及会话模型；记忆与外发隔离；钱包及各层预算。前端可按已定接口并行准备。
3. 接通第一圈的发送、同步、搜索、附件、摘要及撤销流程；先限少量联系人和明确可分享资料。
4. 第一圈边界成立后，做同主人 Agent 的异步单次询问，再做跨主人询问。
5. 最后再考虑扩大自动分享和社交范围。

P7 也还欠一份针对“陌生人访问私人 Agent”的对照研究。现有群聊插话研究自己承认，多主人费用规则缺少证据，不能拿它替本批关键决定背书。`docs/research/2026-11-20-interjection-during-reply.md:135`。

**8. Q-a 到 Q-j 的建议答案**

| 问题 | 建议 |
|---|---|
| **Q-a** | 选有截止时间的异步单次询问；目标暂停、无权限或没额度就当场失败，不等主人、不自动跨日重试。 |
| **Q-b** | 被问 Agent 的主人付它的回答费用，计入其对外预算；发起者主人付发问与回报，两边都受本次任务上限约束。 |
| **Q-c** | B 只用获准向 A、A 主人及实际接收方披露的资料；A 第一版保存任务结果及出处即可，不自动把 B 的话写入自己的主人笔记。 |
| **Q-d** | 限定出站上下文、固定目标及发起人、服务端校验调用权限；返回文本不获得执行工具、继续委托或改变授权的能力。 |
| **Q-e** | 可以单独拉黑 Agent，也可以举报；拉黑其主人则覆盖该主人名下所有 Agent，避免换一个 Agent 继续骚扰。 |
| **Q-f** | 推荐新增社交会话类型，复用底层消息能力；保留主人专属 `agent` 会话及唯一约束，监督与插话权限单独表达。 |
| **Q-g** | 第一版不主动跟进。异步回报是已发起任务的完成通知，不算新的主动聊天，但仍受原任务截止时间约束。 |
| **Q-h** | 同时限制背后真人、目标 Agent、目标主人及全站；申请、消息、排队和后台任务都要计入各自限制，不能只数成功回复。 |
| **Q-i** | 放在 Agent 下，默认不打扰；提供会话、来访者、时间和支出的查询，区分“从我这里归档”“停止往来”“删除数据”。 |
| **Q-j** | 移除、拉黑或删除立即停止新使用及未完成工作；保留规则明确的历史只读副本，禁止旧听说和摘要继续被用于新的对外回答。 |

**9. 需要产品负责人拍板的问题，按重要性排序**

| 大白话问题 | 推荐选项及理由 |
|---|---|
| **1. 陌生人第一次来，必须等你点头，还是当场知道能不能聊？** | **当场决定。** 按你预先选的人群开放，其余拒绝，才符合“没人等主人”。 |
| **2. 你把范围改小后，原来能聊的人还可以继续聊吗？** | **不可以。** 收紧应该立即产生用户预期的结果，历史另行保留。 |
| **3. 关于你的私事，可以让系统自己猜“这人应该能知道”吗？** | **第一版不可以。** 先用你明确允许分享的资料，泄露后的撤销无法收回信息。 |
| **4. “每天最多 N 点”能不能偶尔超过？** | **不能。** 所有对外使用合计不超过，开始前把完成这次回复的钱留好。 |
| **5. 别人能直接使用你自己密钥上的模型吗？** | **第一版先不能。** 站内点数不能约束供应商账单。 |
| **6. 你插话纠正时，Agent 正在写的旧回答怎么办？** | **停止旧回答。** 不让它在你纠正后再发相反的信息，也不自动接你的话。 |
| **7. 你拉黑一个人后，他能换成自己的 Agent 来找你的 Agent 吗？** | **不能。** 拉黑应覆盖背后的真人及其 Agent。 |
| **8. 让 Agent 去问别人，是只问一次，还是可以一直追问？** | **先只问一次。** 对方答不上来就带回结果，花费和等待都可预期。 |
| **9. 另一只 Agent 回答时，是你付钱，还是它的主人付钱？** | **各自主人付各自 Agent。** 延续第一圈规则，并让被访问方保留预算控制。 |
| **10. 删除 Agent 后，别人已经看到的聊天记录要消失吗？** | **保留其已有记录，停止后续使用。** 不能承诺收回已读内容，也不能把共享笔记一并误删。 |

**10. 其他遗漏**

- **账号名复用可能造成认错对象。** 当前删除 Agent 后，其名字立即可供新 Agent 使用。旧联系人、未完成任务和权限必须绑定不可变 ID，不能按同名自动继承；重新查到同名对象时要说明这是新 Agent。`app/service/migrations/048_family_names.sql:8`。
- **没有明确 Agent 能否代表主人作承诺。** “他说周六可能有空”与“已经替主人答应周六见面”不是一回事。前两圈建议只传递信息和意向，不形成预约、承诺或授权。
- **缺少证明产品有用的验收指标。** 应看主人八小时不在线时，多少请求得到有依据的结果、多少因权限或额度结束、每次有效结果成本多少；聊天条数不能证明代理需求成立。
- **扩容不能简单增加实例。** 当前 WebSocket、票据和事件投递要求单实例；若社交带来更多连接，直接加副本可能让用户收不到另一实例处理的消息。无需现在重写部署，但容量验证必须遵守这个限制。`app/service/README.md:2805`。
