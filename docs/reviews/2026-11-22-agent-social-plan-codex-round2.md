**2. 对 C1–C5 的意见**

**C1：同意“次数和站内点数分别限制”；不同意“有次数上限，因此 BYOK 第一版就安全”。**

先把“次数”定义清楚。它应该限制**获准启动的回答任务**，不是最终发出的消息条数：

- 启动前原子预占次数，已使用和在途预占合计不得超过上限。
- 尚未调用任何收费服务便被拒绝，可以释放预占；已经开始调用后，即使失败、取消或没发出答案，也不能简单退回次数。
- 一次任务包含有限的模型轮次、工具调用和重试；这些不能各自获得一份新预算。
- 接话、重试、重新排队都必须保留原任务及发起人身份。

否则，攻击者可以反复诱发失败或取消：供应商已经收费，产品统计仍是“今天回复 0 次”。

三种执行方式的结论不同：

| 情况 | 两层限制能保证什么 | 还缺什么 |
|---|---|---|
| 站点模型 | 次数限制任务数量，点数限制站内支出，方向成立 | 所有收费步骤，包括收尾回答，都必须先取得预算；多个 Agent 共用原子预留 |
| BYOK | 次数限制由本站启动的任务数量；点数只限制其中的站点收费项目，例如本站搜索 | 供应商模型调用、输入输出、重试和后台记忆工作需要独立的资源边界；20 点不限制供应商账单 |
| 以后接入的外部 Agent | 本站只能直接限制自己发出的任务数量和本站费用 | 外部执行器必须能执行截止时间、工作量上限、取消和去重；只限制返回消息数约束不了其内部工作 |

这不是假设中的代码差异。当前：

- BYOK 在 `admit` 中直接返回零模型预留；`settle` 只给站点模型计算模型费用。见 [app/service/src/metering/admit.ts:178](E:/Agent-Family/.claude/worktrees/agent-family-review-8a6084/app/service/src/metering/admit.ts:178)、[app/service/src/metering/settle.ts:109](E:/Agent-Family/.claude/worktrees/agent-family-review-8a6084/app/service/src/metering/settle.ts:109)。
- 一次回复能够包含多轮模型调用、工具执行和收尾调用，失败后还可能创建重试 run。见 [app/service/src/agents/runtime/worker.ts:531](E:/Agent-Family/.claude/worktrees/agent-family-review-8a6084/app/service/src/agents/runtime/worker.ts:531)、`app/service/src/agents/runs.ts:1712`。
- BYOK 记忆模型不受站点记忆额度限制。见 [app/service/src/memory/call.ts:95](E:/Agent-Family/.claude/worktrees/agent-family-review-8a6084/app/service/src/memory/call.ts:95)。
- BYOK 使用本站搜索仍消耗站点点数；迁移 `065_web_search_rules.sql` 明确支持这种组合。

因此，**“回复 50 次”并不等于“调用供应商 50 次”，更不等于可承诺的供应商费用上限。**

我的第一版建议是：

1. 新增的跨主人私聊、代办先开放站点模型。
2. BYOK 在补齐每任务及每日调用／token 边界、失败计数、衍生后台工作的归属之前，不因加了次数开关就开放。
3. 若这些边界能在第一版完成，我不反对第一版开放 BYOK；但文案必须明确“站内点数不含供应商费用”。若要承诺供应商金额硬上限，还需要供应商侧可执行的限额，不能拿本站估算冒充。
4. 外部 Agent 本批只定接入条件，不建设一套通用外部计费系统。不能执行上述约束的执行器，暂不开放给别人调用。

这里说的是**新增社交入口**。现有群聊已经支持 BYOK，不能把它描述成尚未存在，也不能借本次评审默默关闭；旧群聊的限制迁移应单独写清楚。

**“每位来访者最多占一半”：不建议作为默认硬规则。**

只有一位经常联系的同事时，他用到 25 次或 10 点就被拒绝，剩下一半永远闲着；总次数设为 1 时，取整还会产生零次或破坏“一半”的问题。另一方面，这也不是多人公平的保证：不同账号仍可合计耗尽总额度。

更简单的默认方案是：

- 主人级总次数、总点数；
- 每位来访者跨 Agent、跨入口合并的短时限速和并发限制；
- 主人能查看谁用了多少，并停止其使用。

**这个简化方案保证总量和短时占用有界，不保证一个人全天绝不耗尽总额。** 如果产品确实要求后一项，就必须保留独立的每人每日额度，并接受剩余额度不能充分使用的取舍，不能声称两者兼得。无须现在把“一半”写死，更不能把 50／20 当成已经验证的合适默认值。

整体上，我建议保留“两项用户可理解的总上限”，内部统一约束“一次任务最多做多少工作”，不要再叠加一整套首次发布就要调节的比例和分配规则。

**C2：同意保留第一圈；学习闭环是理由之一，但不能是唯一的价值证明。**

没有日历，仍可以回答主人允许公开的饮食偏好、联系办法、公开项目介绍，也可以提供分享助手的能力。这些是真实可用的起点，无须等到能够执行任务才建设。

学习闭环的验收应是：小周第一次问，Agent 没有依据便如实回答；主人后来允许向小周分享某类资料；小周下一次再问，得到有依据的答案。不是“产生了很多建议卡片”，也不是“自动解锁了很多笔记”。

按 A4 尚待审批的联系人请求，应单独统计；不能和已经获准聊天后仍答不上来的问题混成一个失败率。

**C3：同意现在把对外人格规则用于群聊。**

主人在群里，不代表每次模型生成前都会检查，也不代表完整私人设定适合给其他成员知道。现有群提示确实直接拼入完整 `agent.persona`，见 [app/service/src/agents/runtime/prompt.ts:803](E:/Agent-Family/.claude/worktrees/agent-family-review-8a6084/app/service/src/agents/runtime/prompt.ts:803)。

变得平淡应靠完善可分享的语气、表达习惯和角色设定解决。可以后台生成拆分候选，让主人选用，不必让他重写。发布时明确告知群内行为会变化，并让在途回复、后续上下文采用新的对外版本；不能只给新增私聊换提示。

**C4：同意，由模型自然回答，但不要把被隐藏的信息交给它来帮助拒绝。**

“没有可用资料”时，模型可以说明自己无法确认、建议直接问本人。这仍是正常回答，正常占用次数和预算。

不要向模型注入“主人有一条关于某疾病的秘密，但不准告诉你”。这样的拒绝上下文自己就携带秘密，还可能让“我不能说”变成对秘密存在的确认。模型只得到获准资料及一般性的边界说明即可。

没有访问权、暂停、任务超时、预算不足属于执行状态，由系统显示；与内容层面的自然回答没有冲突。

**C5：基本同意钱包先完成，但硬上限的计数与归属规则必须先于硬上限实现。**

钱包已在进行中，没有必要为了形式上的“三路并行”暂停它。权限／会话和记忆／对外人格随后分两路做，也合理。

我建议调整的只有顺序上的这个依赖：先确定 C1 中“一次是什么、谁发起、哪些工作归它、预留何时释放”，再实现硬上限。否则最容易把它写成 `lane='others'` 的计数补丁，之后发现主动回复、重试、后台工作都落在外面。

另外，**当前工作树没有 `app/service/src/metering/pool.ts`**，`admit.ts`、`settle.ts` 仍按单一 `charge_to` 工作。我不据此否认另一条开发线的进度，但“随机不变量测试、第三轮纸面攻击通过、接线进行中”在本轮只能记录为作者提供的信息，不能当成本地已经核实的基础。

**3. 对 D1–D6 的意见**

**D1：采用立即返回任务状态的异步工具；回报是原任务的一部分，不是普通聊天自动再开一轮。**

可以保留 `ask_agent` 这个名称，但需要以下约束：

1. **先固定授权对象，再生成外发问题。** 服务端绑定目标不可变 ID、发起真人、原始指令、回报会话、截止时间及预算。外发问题由 B3 的隔离上下文生成。不能由读过 vault 的私聊模型提供任意 `question`。
2. **返回真实状态。** 只是持久化并排队，就返回 `queued` 和任务 ID；只有实际投递后才能表示“已经问了”。这属于工具结果／系统状态，不是伪装成 Agent 的固定台词。
3. **不等待新增授权。** 目标尚未允许该 Agent 访问，本次任务立即结束；联系人申请可以遵守 A4 独立存在，但七天内获批也不能复活旧任务。
4. **提前给回报留预算。** A 主人承担问题生成与一次结果回报；“digest + report”可以合成一次受限调用。B 的回答另受 B 主人的额度约束。双方预留分别管理，不需要跨主人持有一个长数据库事务。
5. **回报 run 继承 `errand_id`、截止时间和剩余预算。** 即使运行在 `own` lane，也不能取得一份无关的新预算。
6. **结果正文按不可信材料处理。** “由系统投递”不等于把 B 的原话放进 system 指令。回报步骤只看原任务和结果，不获得继续外发、跨会话搜索或修改记忆的权限。
7. **一次终态、一次回报。** 重启或重复事件不能重复报告；主人取消、原会话话题已结束、权限失效或超过截止时间时，不再突然启动普通回复。失败直接显示系统结果，不另外付费解释。

这比“向专属会话塞入一条消息，然后让现有触发器自然处理”多了一层明确的任务状态，但它正是一次委托不会变成持续自动对话的保障。

**D2：同主人也用同一套异步机制，不做第二套同步路径。**

同主人只省去了跨主人的联系人授权检查，没有消除等待占用、重试、取消和预算问题。现有 worker 仍受 `inFlight.size < maxRunsInFlight` 限制，父 run 等待子 run 的问题不会因主人相同消失。见 `app/service/src/agents/runtime/worker.ts:813`。

“没有隐私边界”也不准确：

- `owner_notes` 是共享笔记，但 Agent 可以关闭 `sharedNotes`。
- `agent_notes`、人格、专属会话、文件不是因此全部共享。
- `memory=false`、`sharedNotes=false` 必须继续有效。
- vault 不能因为接收方也属于同一主人，就被带进 Agent↔Agent 会话。

当前 `notesFor` 明确执行这些开关，见 [app/service/src/memory/store.ts:145](E:/Agent-Family/.claude/worktrees/agent-family-review-8a6084/app/service/src/memory/store.ts:145)。同主人任务应复用已有共享资料能力，不隐式扩大范围。

**D3：必须比现有 `open` 更严格，不能直接迁移这个布尔值。**

现有“非 vault”至少可能来自模型分类、主人手工选择，以及 `new_notes='open'`。尤其最后一种直接放行，根本不经过内容判断；因此它不能表示“已经确认无害”。见 [app/service/src/memory/sort.ts:125](E:/Agent-Family/.claude/worktrees/agent-family-review-8a6084/app/service/src/memory/sort.ts:125)。

我建议第一版给“明显无害”一份很窄的定义：

- 可以包含不涉及私人事实的 Agent 工作方式，以及不带原因、时间地点或第三人信息的普通称呼、表达形式、一般口味偏好。
- 健康、具体作息或行踪、关系评价、家庭情况、工作变动、未公开计划不属于这一层。
- 一条笔记混有允许和不允许的内容，原条目不直接放行。
- 旧 `open` 笔记重新按新规则处理，不批量变成“可以对别人说”。

“主人批准此人和 Agent 聊天”只解决访问资格，不表示此人适合知道所有过去在群里可用的笔记。对另一主人的 Agent，继续严格执行 A2 的“仅明确允许资料”，不能沿用真人的无害层权限。

**D4：需要独立的查看进度，不需要建设第二个通知收件箱。**

最小版本：

- 监督会话留在 Agent 的“与别人聊过”列表。
- 主人每个监督会话保存一个私有的“查看到哪里”，只用于本列表的新活动标记和多设备同步。
- 不进入主聊天列表的未读总数，不默认发声音、推送或逐条提醒；访问记录不发送给来访者。
- 联系人申请留在联系人页面；学习建议按 A2 放回专属会话并合并呈现。
- 主人自己发起的代办，最终回报在原专属会话正常出现，不再从监督列表额外通知一次。

当前 sync 会对当前 membership 统一计算未读，`ChatList.jsx` 也直接使用会话排序列表，因此不能只在页面上隐藏几行。见 `app/service/src/sync/read.ts:112`、`app/web/src/pages/ChatList.jsx:88`。

**D5：群聊可以不要求先加 Agent 好友，但明确撤权必须压过群聊使用资格。**

当前代码确实检查群成员、双向拉黑和 `groupMentions`，没有要求 friendship。见 [app/service/src/agents/runs.ts:1032](E:/Agent-Family/.claude/worktrees/agent-family-review-8a6084/app/service/src/agents/runs.ts:1032)。

我不同意由此推出“移除联系人以后，群里仍然可以继续调用”。按 A1 已定结果，被收紧范围或删除关系撤权的人不能继续使用；允许他换到共同群里 @，就让 A1 失效了。

具体替代方案是：

- 普通群成员仍可依据群规则获得调用资格，不强迫他们先加好友。
- A1 的当前禁止范围、明确撤权和双向拉黑，作为更高优先级的拒绝条件。
- 同一条件覆盖直接 @、经 Agent 转述、排队、重试及主动回复候选。
- 禁止继续调用，不意味着删除双方原本有权阅读的群历史。

这里需要统一的是撤权规则，不是把群聊也改成好友聊天。

**D6：建议本批交付第一圈及同主人单次代办；跨主人代办作为后续独立发布。**

跨主人代办同时增加另一套访问资格、第二个付费方、双主人监督和对外资料限制。同主人版本能先验证异步排队、截止时间、去重、取消和一次回报；第一圈能验证跨主人访问、对外记忆和预算。

两部分分别站稳后，再组合跨主人代办，问题更容易定位。保留跨主人目标和接口约束，不必现在把它绑定为同批必须上线的功能。这是我的范围建议，作者尚未给出最终立场。

**4. 本轮新增的问题：不重复第一轮已经指出的事项**

**① C1 的总上限不能只挂在 `others` lane。**

一个人不用 @，靠普通群消息持续触发主动回复，费用就可能走 `proactive`。目前这类 run 的 `caller_id` 是 `null`，预算也与 `others` 分开。见 [app/service/src/agents/proactive/decide.ts:284](E:/Agent-Family/.claude/worktrees/agent-family-review-8a6084/app/service/src/agents/proactive/decide.ts:284)、`app/service/src/agents/runs.ts:978`。

新的主人级对外总额应覆盖这两类支出；现有主动回复预算可以继续作为更低的子上限。不能把“不能明确分到某位来访者”解释成“不计总额”。

**② A1 需要保存“这份访问资格为什么存在”。**

现有 `friendships` 只有双方 ID 和 `since`，不足以区分主人亲自批准、依据主人联系人自动获得资格、依据某条范围规则获得资格。见 `app/service/migrations/002_core.sql:49`。

例如小周先因“我的联系人”进入，后来主人又单独批准过他；删除真人好友时应该撤掉哪份资格，必须有记录可判断。建议保存授权来源、适用范围和关系版本；明确撤权优先。不能删一条 friendship 后又被另一条自动规则悄悄补回来。

**③ 两个代办不能被现有聊天合并机制合成一个回答。**

主人先让 A 问 B“报价”，随后又让 A 问 B“周六安排”。现有机制按 Agent×会话只允许一个活跃 run，后续消息可被折入该 run。见 `app/service/migrations/016_agents_in_groups.sql:4`、`app/service/src/agents/runs.ts:794`。

代办必须按 `errand_id` 关联问题、回答、预算和回报。第一版可以让同一对 Agent 的代办顺序执行，但不能合并任务，更不能把第二个答案交回第一个任务。

**④ 切换模型或供应商后，旧社交资格不能直接绕过执行条件。**

例如一个已开放的站点模型 Agent 改成 BYOK，原有联系人无需重新加好友便能触发外部支出。访问资格可以保留，但每次开始任务都必须重新确认当前模型来源满足社交执行条件；不满足时显示暂停可用状态。

这是运行资格检查，不必再增加一次联系人审批。任务已经预留的价格、模型和资源边界也不能在重试时无声换成另一套。

**⑤ “发布前检查”包括中途确认语，不只包括最终答案。**

当前工具循环会在执行工具前发布模型生成的 `acknowledgement`，见 [app/service/src/agents/runtime/worker.ts:690](E:/Agent-Family/.claude/worktrees/agent-family-review-8a6084/app/service/src/agents/runtime/worker.ts:690)。如果只在最终答案落库前复查许可，前面已经发出的文字仍可能使用旧许可。

第一版最简单的做法是社交回复只显示系统“正在回复”，最后一次性发布答案；如保留中途文字，每次发布都执行同样的权限及版本检查。不能把一次逻辑回答直接等同于一次消息发布。

**5. 我建议的最终施工顺序**

与 E 大体一致，但把硬上限所依赖的规则提前：

1. **先收敛本轮规则。** 明确计数单位、预算归属、撤权优先级、无害层、人格迁移、代办范围；状态表和 P7 对照研究一起交付。
2. **完成钱包，再接硬上限。** 钱包工作可继续；硬上限按第 1 步的约定实现，并明确现有群聊和 BYOK 配置如何迁移。
3. **开展两条实施线。** 一条做权限、`agent_social`、监督及读取入口；另一条做对外人格、A2 记忆规则、许可失效和学习建议。共享同一份身份、受众和版本定义。
4. **接通第一圈并小范围验收。** 同时覆盖群聊的对外人格与撤权适配；再做真实模型、恶意输入和并发撤权验证。默认审批、超时、预算不足分别统计。
5. **交付同主人异步单次代办。** 验证持久化任务、预算保留、重启去重、取消、顺序执行和一次回报。
6. **跨主人代办独立发布。** 以前两部分已经成立为前提，再接第二付费方、跨主人许可及双主人监督。

这些是后续施工与验收要求，本轮没有执行其中的测试、构建或发布。
