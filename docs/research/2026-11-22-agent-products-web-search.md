# How agent/chat products give the model "web search" (research, read 2026-11-22)

Scope: Cherry Studio, Hermes Agent, OpenAI Codex CLI, OpenCode, plus Claude Code and LibreChat for comparison. Primary sources only (official docs, release notes, PR pages used to confirm behaviour). Anything I could not confirm is marked "not verified". No source code was read or copied (Cherry Studio is AGPL).

Mechanism key: (i) provider built-in search switched on in the API request; (ii) separate search service with the user's own key; (iii) free / no-key path; (iv) service hosted and paid by the product vendor.

## 2. Per-product notes

### Cherry Studio (desktop, AGPL: behaviour only)

- Online mode docs, read 2026-11-22: https://docs.cherryai.com.cn/docs/en-us/pre-basic/settings/websearch.md . Globe icon in the chat input turns online mode on "for the current conversation only". Two paths: the configured search service, or the model's native search (a small globe next to the model name marks support; examples named: DeepSeek, OpenRouter, Alibaba Bailian, some Gemini/Zhipu/xAI Grok models; some, like Volcengine, can go online without the icon).
- Defaults per that page: built-in Exa MCP search provider needs no key; Jina is the default URL fetcher; the "Prefer configured search service" toggle is on. Result count 5 (max 100); compression default truncates at 2,000 chars; a blocklist exists. Provider list: Exa MCP (default), Tavily, Bocha, Exa, Zhipu, Querit, SearXNG, Firecrawl, Jina.
- Free options page, read 2026-11-22: https://docs.cherryai.com.cn/docs/en-us/pre-basic/settings/websearch/free-search . Names Exa MCP (default, public endpoints, no key) and self-hosted SearXNG (unlimited calls). It does NOT mention a local Google/Bing/Baidu hidden-window scraper.
- Release notes: v2.1.7 adds DuckDuckGo as a keyless provider and clickable web links in tool results (https://newreleases.io/project/github/CherryHQ/cherry-studio/release/v2.1.7). v2.0.11 says "prefers model-native search by default, with automatic fallback to configured services" (https://newreleases.io/project/github/CherryHQ/cherry-studio/release/v2.0.11).
- PR #19825 (https://github.com/CherryHQ/cherry-studio/pull/19825): setting `chat.web_search.model_tools_preferred`, default true; search and fetch routed independently; fallback is automatic with no off switch (search falls back to Exa MCP; fetch to built-in Fetch, then Jina); a reviewer flagged that a query could silently reach a fixed Exa endpoint, so a tooltip disclosure was added.
- Docs/release conflict: the online-mode doc says "prefer configured service" is on, the PR says "prefer model-native" is default true. Possibly the doc is older or the setting was renamed; I could not reconcile it. Either way, with only a model key the product owner's experience is explained by one of: (a) the model's native search (cost = the provider's per-search fee on the user's own model account, if the provider charges one), or (b) keyless Exa MCP via a public endpoint (free to the user, the query goes to Exa). Which one fired depends on the model and app version; I cannot tell which from docs alone.
- Google/Bing/Baidu: a third-party search summary claimed a built-in Google/Bing/Baidu "free search" with a search-enhancement toggle, citing a Traditional Chinese docs page. I could not open that page (404 on the mirror), and the English free-search page does not list them. Treat as not verified. Cherry's SearXNG docs say its default engine selection includes Google and suggest forcing Baidu for mainland China (via SearXNG settings), which is SearXNG, not a local browser.
- Firecrawl keyless search/fetch: stated in docs PR https://github.com/CherryHQ/cherry-studio-docs/pull/123 (maintainer-confirmed there).

### Hermes Agent (Nous Research)

- Web search docs, read 2026-11-22: https://hermes-agent.nousresearch.com/docs/user-guide/features/web-search . Tools `web_search` and `web_extract`. Backends and keys as in the table. Selection order: `web.search_backend` / `web.extract_backend`, then `web.backend`, then auto-detect from env vars (order: Tavily, Perplexity, Exa, Parallel, Firecrawl, Nous Tool Gateway, SearXNG, Brave, DDGS, then the keyless ring). xAI is never auto-detected. With nothing set, requests rotate across free tiers and fail over on rate limits ("strictly last-resort"). `web.keyless_fallback` default on.
- Tool Gateway, read 2026-11-22: https://hermes-agent.nousresearch.com/docs/user-guide/features/tool-gateway . Paid Nous Portal subscription, billed "pay-as-you-use" to the subscription; no per-search price given; not on by default (enabled via `hermes setup --portal`, `hermes model`, or `hermes tools`); free pool exists but page says it is limited to image models. Search and extract can be routed separately.
- Tools page: https://hermes-agent.nousresearch.com/docs/user-guide/features/tools (toolsets per platform; `hermes tools`). Default-enabled toolsets not stated.
- Security page: https://hermes-agent.nousresearch.com/docs/user-guide/security . Blocklist/SSRF details as in the table. The page does not say fetched web content is scanned for injection.

### OpenAI Codex CLI

- Web search page, read 2026-11-22: https://learn.chatgpt.com/docs/web-search (redirect target of developers.openai.com/codex/web-search). Cached default for local chats; live by default under full access; `--search` for one live run; hosted tool separate from sandbox networking; "Treat all web results as untrusted input".
- Config reference, read 2026-11-22: https://learn.chatgpt.com/docs/config-file/config-reference . `web_search` = disabled / cached / indexed / live (default cached; full-access flips to live); `tools.web_search` object with `context_size`, `allowed_domains`, `location`; legacy `features.web_search*` deprecated; `model_providers.<id>.capabilities.external_web_access` and `supports_standalone_web_search` (default false, "still under development") for non-OpenAI providers; `memories.disable_on_external_context` keeps threads that used search out of memory generation.
- CLI page: https://learn.chatgpt.com/docs/codex/cli (search activity "stays visible in the transcript").
- Underlying API tool (for the hosted-tool mechanism), https://developers.openai.com/api/docs/guides/tools-web-search : inline `url_citation` annotations, `sources` list, up to 100 allowed or blocked domains, `search_context_size` low/medium/high, context capped at 128k, tool-call cost on top of tokens (price not read here). Billing for Codex specifically: not verified.

### OpenCode

- Web search page, read 2026-11-22: https://opencode.ai/docs/websearch/ . Providers Exa, Firecrawl, Parallel, Tavily, TinyFish; keys via `/connect` or env var; first search asks permission and provider choice and remembers it; `websearch.provider` in `opencode.jsonc` (a provider ID or `"random"`); 429 cooldown per provider (Retry-After, else 60 s); `websearch` is a permission action; `websearch: false` removes the tool. The page names no default provider and does not say who pays.
- Hosted search billing, read 2026-11-22: https://opencode.ai/docs/console/websearch/ . $0.01 per successful search charged to the workspace balance, up to eight results, shown separately from model usage; own `websearch.provider` overrides the hosted one.
- Tools page: https://opencode.ai/docs/tools/ (`webfetch`: one HTTP/HTTPS URL, markdown/text/html, timeout up to 120 s; both tools permission-gated).
- Community sources (forum/blog, NOT primary, so treat as unverified) claim older versions enabled search only for the OpenCode Zen provider or when `OPENCODE_ENABLE_EXA=true`, calling Exa's hosted endpoint with no key. The current official page does not describe this.

### Claude Code (comparison)

- Tools reference, read 2026-11-22: https://code.claude.com/docs/en/tools-reference . WebSearch uses Anthropic's web search backend, returns titles and URLs only, up to eight backend searches per call, allowed or blocked domains (not both), backend not configurable (add an MCP search server for another provider); not available on Amazon Bedrock. WebFetch: separate model call reads the page; permission rules `WebFetch(domain:...)`; both tools are in the "permission required" column.
- API tool, read 2026-11-22: https://platform.claude.com/docs/en/agents-and-tools/tool-use/web-search-tool . $10 per 1,000 searches plus tokens (results count as input tokens); failed searches not billed; `max_uses` per turn; citations always on, `cited_text` up to 150 chars; enabled for an org unless an admin disables it or restricts domains in Console; displaying output to end users requires showing citations. Whether Claude Code subscription plans meter searches: not verified.

### LibreChat (comparison; better documented than Open WebUI for server-held keys)

- Web search config, read 2026-11-22: https://www.librechat.ai/docs/configuration/librechat_yaml/object_structure/web_search . Provider lists, defaults and limits as in the table. Enabling per chat: "+" in the composer, gear on the Web Search row, pick provider, add keys; then select Web Search (a chip shows while on). Admin may configure SearXNG for everyone in `librechat.yaml`. Billing terms not given; says server keys are admin-owned and Tavily advanced search/extract cost more credits.
- Open WebUI (checked via search snippets only, so not relied on): admin-level engine and key, per-chat toggle via "+", Tavily key page https://docs.openwebui.com/features/chat-conversations/web-search/providers/tavily.md (default toggle state not stated; no pricing).

## 3. Synthesis: four patterns

1. Provider built-in search (Codex hosted tool, Claude API tool, Cherry model-native, Hermes xAI/OpenAI-native). The request just carries a tool flag. User configures nothing beyond the model key. The provider bills per search on top of tokens (Anthropic $10 per 1,000; OpenAI "tool call cost"). Citations come back structured, which is the best UI feed. Weakness: only for models/providers that support it, differing formats per provider, and no control over the engine. Feasible hosted. Cost lands on whoever owns the model key: with bring-your-own-key users it is their bill (and they can be told "searches may add fees"); with server-held model keys it is the operator's.
2. Separate service with a key (Tavily, Exa, Brave, Firecrawl, SearXNG; OpenCode, LibreChat, Cherry, Hermes). Works with any model, including ones with no native search. Feasible hosted: the operator holds one key and pays per query, or each user brings their own (LibreChat prompts per user; OpenCode lets a member override the workspace provider). Cost is predictable per search but must be rate-limited and metered by the operator.
3. Free / keyless (Cherry's Exa MCP and DuckDuckGo, Hermes' keyless ring and DDGS, LibreChat's Keenable, self-hosted SearXNG). Zero cost to set up, but quality and rate limits are best-effort; hosted use from one server IP is the likely failure mode (Hermes documents rotation and failover for exactly this). Fine as a fallback; weak as the only path. A local hidden-browser scraper is not documented in the sources I could read, and is not feasible hosted anyway.
4. Vendor-hosted and vendor-paid (Nous Tool Gateway on a subscription; OpenCode hosted search at $0.01, visible as its own line in usage). Cleanest for users (no key, one bill), but the vendor must meter, cap and price it, and the page-level documentation of limits is thin (Hermes gives no quota). For a hosted product this is the "operator holds the key" model made explicit.

Implications for a hosted product where users may bring a model key: a layered design matches what Cherry (native first, then service, then keyless fallback) and OpenCode (ask once, remember) do: use the model's built-in search when the model supports it (bill to the key owner), else the server's search key under a per-user/per-day cap, with a keyless provider only as a last resort. Whatever is chosen, disclose when a query goes to a third party (Cherry added a tooltip for exactly this), show citations/source links (Anthropic requires it for end-user display; OpenAI requires clickable links), keep fetch separate from search (every product does), and treat results as untrusted (Codex says so explicitly; Hermes' blocklist does not cover search).
